# 规则评测集

这几十行 CSV 的用途只有一个：**在接 LLM 之前，先量出关键词规则到底有多差**。

没有这个基线，「LLM 有没有用」就只能靠感觉。而感觉在这件事上尤其不可靠——
模型把「转账」翻成「客户回款」时看起来非常合理，只有对着标注才知道它错了。

## 怎么用

```bash
# 1. 把一份银行流水导出成待标注的表
npx ledgerlint ./mybook --export-cases 流水.csv --out cases.csv

# 2. 手工给每行填 expected_event（以及可选的 expected_accounts）
#    认不出就填 E99 —— 留 E99 永远比猜错好

# 3. 打分
npx ledgerlint ./mybook --eval cases.csv
```

## 列的含义

| 列 | 说明 |
|---|---|
| `direction` | `IN` / `OUT` |
| `amount` | 元，两位小数 |
| `expected_event` | 你判断它应该归到哪类事件，`E1`…`E16`；认不出写 `E99` |
| `expected_accounts` | 可选，`/` 分隔的科目编码集合。留空则只比对事件，不比对科目 |
| `note` | 给自己看的备注，不参与打分 |

## 打分怎么读

| 结果 | 含义 | 严重度 |
|---|---|---|
| 事件判对 | 完全一致 | — |
| 事件对、科目不同 | 归类对，但分录落错科目 | 中 |
| 该识别却落 `E99` | 漏判。**显形**，用户会在待处理里看到 | 低 |
| 不该识别却识别 | 把补助、退税、押金记成了收入 | **高** |
| 判成了别的具体事件 | 归错类，且看起来很合理 | **最高** |

后两类会让进程以退出码 1 结束——**错账比空白更难发现**，所以它们必须能卡住流程。

## 关于样本量

`cases.csv` 现在只有 8 条，是用来跑通流程的冒烟集，**不足以支撑任何结论**。
D007 定的门槛是 **50 条真实流水**，且必须来自真实企业（G2），不能是自己编的。
