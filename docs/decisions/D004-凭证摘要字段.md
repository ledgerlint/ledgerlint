# D004 · 凭证摘要字段（契约追加）

- **状态**：已批准，待实施
- **日期**：2026-11-09
- **裁决人**：交付总监
- **触发**：T05 工程师上报「手工凭证的摘要无处安放，被临时塞进 `ruleSnapshot.SUMMARY`」

---

## 一、问题

`PostedVoucher` 冻结时没有摘要字段。规则生成的凭证可以借 `RuleHit.oneLiner` 充当摘要，但：

- `MANUAL`（手工录入）与 `REVERSE`（红冲）凭证没有 `RuleHit`
- 工程师的变通做法是把摘要写进 `ruleSnapshot.SUMMARY`

**这个变通必须驳回。** `ruleSnapshot` 的语义是「落账时生效的规则及版本」，是**配置快照**；往里面塞叙述文本，会导致：
1. 该键无 schema 约束，可以被任何调用方写入任意内容
2. 三个月后没人记得这个约定，交付包就会少一列
3. 摘要本应进哈希（可检出篡改），而 `ruleSnapshot` 虽进哈希，却把「我说了什么」伪装成「规则是什么」

## 二、为什么必须现在加，而不是"以后再补"

| 现在加 | 以后加 |
|---|---|
| 成本 ≈ 0：尚无任何真实凭证，规范序列化改一次即可 | 需要**断链迁移**：全部历史凭证 hash 失效，或写一版兼容序列化 + 双链并存 |
| 只改一个字段 + 一处顺序常量 | 要写迁移脚本、要说服自己"旧账不可信" |

这正是 D001 说的「唯一一处事后改不起的地方」。**摘要属于凭证的事实内容，不是可选展示字段**——会计翻开凭证，第一眼看的就是摘要；没有摘要的借贷两行，无法判断这是销售、借款还是转账。

## 三、设计

```ts
export interface PostedVoucher {
  // ...
  /** 摘要。必填且非空。 */
  readonly summary: string;
  // ...
}
```

| 决策 | 内容 |
|---|---|
| 粒度 | **凭证级**，不是分录级。MVP 一张凭证=一个经济事件，分录级摘要留到 v0.2（若真实账暴露一借多贷需分述再加） |
| 必填性 | `string`，非可选。空串或纯空白视为非法（与 `counterparty` 同一条规则：空格不算填了） |
| 进哈希 | **是**。位于规范序列化顺序中 `voucherDate` 之后、`lines` 之前 |
| 来源 | `IMPORT` → 取 `RuleHit.oneLiner`；`MANUAL` → 用户输入（≤40 字）；`REVERSE` → 自动生成「红冲 记-0001」 |
| 上限 | 40 字。理由同 `oneLiner`：长了没人读，没人读等于没有解释 |

## 七、工程师上报的四个问题及裁决

### 7.0 先纠正一条错误记录

**上一提交 `d69c08b` 的信息声称「收窄 source 至 IMPORT | MANUAL | REVERSE，删除 RECON」，实际未删**——`types.ts:356` 仍是四个值。

这是「文档与代码不同步」的典型样本，且发生在提交信息里（比文档更隐蔽：没人会去 diff commit message 与代码）。以下 7.1 的处理同时修正它。

### 7.1 `RECON` 无摘要来源 → **删除 RECON**

| 选项 | 判断 |
|---|---|
| 保留 RECON，约定摘要模板「勾稽调整：<差异说明>」 | ❌ 为一个本期不会产生的凭证类型发明约定，是凭空的复杂度 |
| **删除 RECON** | ✅ **采纳** |

理由：MVP 的勾稽（T19）**只出差异清单、不产凭证**。类型里留一个没有任何生产者、也没有摘要来源的值，等于给未来的自己一个「看起来支持」的错觉——这与 BP2「`auxRequired` 声明 21 处、只实现 4 处」是同一种病，只是换了个位置。

若 v0.2 要做勾稽调整凭证，**届时连同摘要来源与格式化规则一起加**，而不是先留个口子。

### 7.2 `oneLiner` ≥41 字会让整张凭证在 `post()` 被拒，且失败点太晚

**裁决**：失败点前移，不在 `post()` 兜底。

- 规则层（T28 依据链 / T20 事件模板）**必须在生成时校验 `oneLiner ≤ 40 字`**，超长即拒绝，并指出**是哪条流水第几行**导致的
- `post()` 的 `assertSummary` 保留长度校验作为最后一道（防线不撤），但**错误文案必须带来源提示**：「摘要最多 40 字（当前 N 字）；若来自规则，请检查该规则的一句人话」
- 理由：用户已逐条确认完、点「生成交付包」时才失败，是最伤信任的失败方式

### 7.3 红冲时凭证号过长，报的却是「摘要超 40 字」

**裁决**：`reverse()` 内**先校验 `voucherNo` 长度**，再拼摘要。报错要指向真正的原因（凭证号过长），不要让调用方去猜摘要为什么超长。

### 7.4 丢了「至少 2 个字」的旧下限，单字摘要（如「租」）现在能过

**裁决**：**不恢复下限**。

理由：任何硬性字数下限都会被「凑字」消解（「租」→「租房费」只多两个字，信息量没增加），而真正的质量标准是**这句摘要能不能让人看懂这笔业务**——那由 A5 可解释率与 X06 盲评来判，不由字数判。

但补一条软要求（不阻塞提交，写入 T28 验收）：**规则生成的 `oneLiner` 必须包含「谁 + 做了什么」两个要素**，例如「收到 XX 客户货款」而非「收款」。
