# D008 · 落账、三表与手工录入的实施记录

- **状态**：已实施
- **日期**：2026-11-10
- **范围**：T34（确认落账）、T10–T12（三表）、T35（手工录入凭证）、并发重复落账的修复

---

## 一、确认落账：归档，不是删除

草稿确认后移到 `drafts/confirmed/YYYY-MM.jsonl`，**不删**。

理由不是洁癖：三个月后有人问「这笔当时系统是怎么判断的」，凭证上只有 `ruleId`，
而当时那句人话（`oneLiner`）和「我猜的」（`assumed`）只存在于草稿里。
删掉之后，只能回答"用了哪条规则"，回答不了"为什么这个科目"。

代价是 `drafts/` 会随时间变长。接受：它是按月分片的纯文本，一年 12 个文件，
且 `readAll()` 只扫顶层 `drafts/*.jsonl`，归档子目录不在读取路径上。

**不做批量事务**：一张失败不影响其他张。失败几乎总是单张的问题（科目被改坏、摘要为空），
整批回滚只会让用户不知道是哪一张坏了，只能重来一遍——而重来一遍要重新导入，
`txnId` 是内容哈希，同一批草稿会以"已存在"被跳过，人就卡死了。

指定 `draftIds` 但 id 不存在时**必须报出来**（"这张草稿已经不在了"）。
静默跳过会让界面显示"没有落账"，而用户明明点了确认——他只会以为按钮坏了。

## 二、三表：未结转为损益单列，不并进未分配利润

MVP 不做结账，所以 5xxx 的余额在期末还挂在账上。资产负债表的权益侧必须包含它，
否则**资产永远不等于负债+权益**（这不是口径分歧，是记账顺序决定的）。

列报位置：**单独一行「本期未结转损益」**，不混进「未分配利润」。
混进去报表会看起来"平了"，但看不出这个数还没结转——模糊的平账比明确的不平更危险。

由此得到一条可断言的勾稽关系：

> `balanceSheet().unclosedPnl === incomeStatement().netProfit`

它成立当且仅当**科目表里每个损益末级科目都在利润表里有位置**。
所以测试不是写死几条凭证，而是遍历科目表逐个造凭证（`reports.test.ts`）。
将来加一个 5xxx 科目却忘了给它在利润表找位置，这条会红——而那种错在界面上
只会表现为"利润表少了一块，资产负债表仍然是平的"，肉眼查不出来。
页面上同样跑这条校验，不成立时出一条红色横幅。

## 三、手工录入：三条边界

1. **校验全部交给 `post()`**。手工录入口只做「界面输入 → 凭证体」的翻译。
   再写一套校验必然与 `post()` 漂移，漂移那天会出现"界面说没问题、落账被拒"，
   或者更糟的反向情况。
2. **不做自动配平**。「差额自动记财务费用」看起来贴心，实际是错账来源：
   用户少填一行，程序替他补一行，账平了，但每一分钱都在错的科目上。
   界面只显示「还差 200.00 在贷方」，不代劳。
3. **不给默认科目**。默认成"库存现金"看似省事，但用户直接填金额就能记，
   记出来的科目十有八九不是他想的那个。科目下拉首项是空的「选择科目…」。

金额在 HTTP 层保持**字符串**形态，直到 `parseYuan` 才变整数分：
`Number('0.1') * 100` 是 10.000000000000002，靠 `roundCents` 能救回来，
但那是把一个输入解析问题交给浮点容差兜。金额是从字符串逐位抄下来的，
就在字符串上算完。

## 四、凭证清单按日期倒序，不按落账顺序

落账顺序由"什么时候点确认"决定，与业务日期无关。用户常常攒一周再一起确认，
按落账顺序排会让 11-04 排在 11-20 前面，看起来像账错了。
显示层排序不影响哈希链（链的顺序是文件写入顺序，永远是权威）。

## 五、并发：一个自测出来的严重缺陷

端到端自测时顺手试了「三个请求同时点确认」，结果：

```
第一轮（未修）：vouchers 4  verify true
  记-0001 v-391bd427 收 杭州甲客户科技有限公司 货款
  记-0003 v-391bd427 收 杭州甲客户科技有限公司 货款   ← 同一笔，记了两遍
  记-0002 v-3aa1b12a 收 上海丙客户 货款
  记-0004 v-3aa1b12a 收 上海丙客户 货款               ← 同一笔，记了两遍
```

链完全自洽：`prevHash` 接得上、`verify` 全绿、凭证号也不撞。
但收入凭空翻倍。这正是 BP2 的死因形状——**绿勾 + 错账**。

根因不是"忘了去重"，是 `confirmDrafts` 的「读草稿 → 写链 → 归档」跨在
`append` 的写锁外面：两个请求读到同一批草稿，各自算出同一个 `voucherId`
（`v-${txnId}`，确定性 ID），然后依次落账。

修法放在**存储层**，而不是每个调用方：

1. `append` 内校验 `voucherId` 全局唯一、`voucherNo` 期间内唯一；
   两个集合在启动扫描时建立，重启后仍然有效（不靠内存记忆）。
2. `postManualVoucher` 遇 `DUPLICATE_VOUCHER_NO` 重取号重试（最多 3 次）——
   撞号不是用户的错，重算一次就好。

修后同一实验：`vouchers 2  verify true`，另两个请求返回 `confirmed: 0`；
并发两张手工凭证拿到 `记-0003` / `记-0004`，各自成账。

这个缺陷不是设计推演出来的，是**跑出来的**。记在这里是因为它说明一件事：
「链校验全绿」证明不了「账是对的」，只有把同一笔业务对着看才能。

## 六、已知缺口（主动记录）

| 缺口 | 现状 | 为什么不现在补 |
|---|---|---|
| 负资产余额不告警 | 库存现金贷方余额 -100 会照常显示，只是标红 | 没有期初余额，任何"现金不能为负"的告警会让每个新账套在第一次记账时误报 |
| 手工凭证不能改、不能删 | 只能红冲（尚未做界面） | 凭证进哈希链即不可变，这是设计而不是待办 |
| 无期初余额录入 | 建账即从 0 开始 | 影响"能不能拿真实历史账套试"，属 G2 之后的下一步 |
| 无结账 | 损益不结转，三表单列 | 结账会冻结期间，属于"难以回退"的设计，需要单独裁决 |
