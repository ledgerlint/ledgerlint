## 一、为什么这件事排在第 2 天，而不是第 20 天

压缩后的开发里，**代码写错是最便宜的错误**（改一行、跑一次测试、5 分钟）。真正贵的是
「语义定错」：它不产生编译错误，只在两周后真实流水上暴露，而那时 B/C/A 三条泳道已经
按错的语义写完了。

开发计划 §5.4 已把代价量化过，这里是执行时的版本：

| 类型 | 冻结失败的代价（原话） |
|---|---|
| `Transaction` | B+C 两条泳道同时停 1 天 |
| `EventKey` | T20–T26 返工 60%，且错配**不会报错**（最贵的失败） |
| `PostedVoucher` + `JournalLine` | 进哈希，字段增减 = 所有历史凭证 hash 失效 = 链要迁移 |
| `AssertionResult` | `limitation` 变可选 → 交付包退化成 BP2 的「绿勾无边界」 |

## 二、六型冻结决议

| # | 类型 | 为什么现在冻结 | 改它要付什么 | 谁有权改 |
|---|---|---|---|---|
| 1 | `Cents` + `Transaction` | 它是 **B 产出 → C 消费的唯一交接面**；字段一改，7 个解析器与 12 类规则同时返工 | `import/` 与 `rules/` 同时返工；幂等键（`txnId`/`fingerprint`）重建，已导入账套要重跑 | **B + C 联署**；A 确认不影响 journal 读回 |
| 2 | `EventKey` | 它是规则库的**值域**。值域不冻结，YAML 与代码会各自漂移且**静默错配** | 改语义（非追加）→ T20–T26 返工 60%，且错配**不报错**；删除任一值 → 历史凭证的 `hit.event` 变成悬空引用 | **C 独占**（只允许**追加**）；追加须通知 A（进哈希）与 D（展示文案） |
| 3 | `RuleHit` + `BasisRef` | `basis` 进哈希链；`CITE` 分支**不可事后追加**（S1，见开发计划 §⑦） | 加字段 = 历史 hash 全部失效；`BasisRef` 少一个 kind → A5「可解释率 100%」永远差一截 | **C 独占**；`CITE` 分支的删除需 A + E 联署 |
| 4 | `JournalLine` + `PostedVoucher` | 它进哈希且是 append-only 的写入形状；字段一变，已建测试账套与示例账套全部重建 | 链迁移 + 示例账套（T31）重建；`periodId` 派生规则失效会让 `read(period)` 分片错位 | **A 独占**；D/E 只读，无权改字段 |
| 5 | `AssertionResult` + `BlockId` | `limitation` 必填是「局限随结论输出」的**编译期兑现**，不是文档承诺 | 改成可选 → 交付包退化为「绿勾无边界」，产品唯一的信任护城河消失 | **E 独占**；`BlockId` 增减需 D 联署（交付包排版） |
| 6 | `JournalPort` | 它是**唯一写入口**。多一条写路径，「凭证不可变 + 链完整」就只是习惯 | 加第二个写方法 = 链完整性失去保证；`append` 开放 `hash` 入参 = 允许手工拼 hash | **A 独占**；B/C/D/E 只读 |

### 2.1 三条从类型里长出来的硬约束（写在这里是为了将来有人问「为什么不能加」）

1. **`PostedVoucher` 没有 `amount` / `accountCode` / `direction` 这类扁平字段。**
   只要有 `amount`，生成式调用（LLM 或模板）就能跳过借贷直接给凭证赋值，而**一张「有总额没有分录」的凭证在任何试算平衡里都是平的**。金额与科目只能存在于 `lines`，合计只能存在于 `totalDebitCents` / `totalCreditCents`，两者是否一致由 B1 判定，**不由类型自动兜住**。
   已被 `types.test.ts` 用 `@ts-expect-error` 反证：加任一个扁平字段，编译失败。
2. **`periodId` 由 `voucherDate` 派生，不许独立赋值。** 期间与日期各存一份，必然出现「12 月的凭证挂在 11 月」，而它从数据表面看不出来。
3. **`AssertionResult.limitation` 编译期必填。** 写的是「这条断言**查不出什么**」，不是「已检查什么」——后者只是自我表扬，前者才是用户决策的依据。同理 `skipped` 与 `passed` 是两个独立事实，汇总必须分列。

## 三、变更签字约定（本阶段一人执行，约定为将来写死）

**改动上述六型的任一**已有字段语义 / 已有枚举值 / 已有字段顺序**，需 A/B/C/D/E 五方签字。**

| 方 | 角色 | 关注点（它为什么有权否决） |
|---|---|---|
| **A** | 内核 / journal 所有者 | `PostedVoucher`+`JournalLine`+`JournalPort` 进哈希；A 改字段 = 链迁移，A 有否决权 |
| **B** | 输入层 | `Transaction` 是它的产出形状；改字段 = 全部解析器返工 |
| **C** | 规则层 | `EventKey`/`RuleHit` 是它的语言；改语义 = 已写 YAML 静默错配 |
| **D** | 界面层 | 依据链、`assumed`、`limitation` 都要被**展示**；改了没人展示等于没改 |
| **E** | 机检层 | `AssertionResult`/`BasisRef` 是它的留痕格式；`limitation` 决定交付包能否成立 |

补充规则：

- **允许的单方动作（无需签字）**
  - B：给 `Transaction` **追加可选字段**；
  - C：给 `EventKey` **追加新值**（不改旧值语义）；
  - E：给 `AssertionResult` **追加可选字段**。
- **一律禁止**：删除已有字段、把可选改必填、把必填改可选、修改 `BasisRef` 已有 kind 的语义、
  给 `PostedVoucher` 加扁平金额/科目字段。
- 违反流程的处理照开发计划 §6.1 信号 2：**停 1 天，五方重签本文件，不允许边写边改**。
- 本阶段只有工程师一人，签字栏为待填；这不是形式主义——**它定义的是将来多加一个人时，
  谁可以单方面改类型**。约定现在写，成本是 0；等到有人已经改了再补，成本是链迁移。

## 四、偏差记录

### 偏差 1：用 **npm workspaces**，不用 pnpm（与开发计划 T01 的产出物清单不一致）

开发计划 T01 的产出物写的是 `pnpm-workspace.yaml`。**实际采用 npm workspaces**，理由：

1. **环境事实**：本机 Node v22.22.2 / npm 10.9.7 / git 2.55.0，**没有 pnpm**。为一个 4 万行的
   单人项目引入一个额外的包管理器，等于给「新用户 clone 后一条命令跑起来」多加一个前置条件。
2. **单人项目**：pnpm 的核心收益（严格依赖隔离、节省磁盘、monorepo 硬链接）在「一个人、
   三个依赖、包之间只在编译期互相引用」的规模上不产生可观测收益。
3. **CI 更简单**：`npm ci` 是 GitHub Actions 的默认路径（`setup-node` 的 `cache: npm` 直接可用），
   不需要额外的 pnpm 安装步骤与缓存配置。

**代价（明确接受）**：

- 将来若引入**幽灵依赖**（写了 `import 'x'` 但 `package.json` 没声明），npm 默认扁平化会**放过**它，
  pnpm 会**报错**。缓解措施：每个包的 `package.json` 必须显式声明自己用到的依赖，review 时检查。
- 根 `package.json` 的 `typecheck` 要显式列出五个包（`npm run typecheck -w ... -w ...`），
- 换包管理器时**不能**只换 lockfile：`package.json` 的 `workspaces` 字段是 pnpm 也认的，
  所以反向迁移成本很低（保留 `workspaces` 字段即可）。这也是选 npm 的一个理由：
  **它没有把项目锁死在 npm 上**。

### 偏差 3：`vitest` 取 **5.x**，不是 2.x

依赖清单仍严格限定在 `typescript` / `vitest` / `@types/node` 三个之内，只是版本取 5.x：

- **实测原因**：`vitest@2`（及其依赖 `esbuild` / `tinypool` / `@vitest/mocker`）在 `npm audit` 下报
  **6 个漏洞（含 2 critical）**；`vitest@3` 仍报 3 个（含 2 critical）；**`vitest@5.1.0` 为 0 漏洞**。
- 这些漏洞只存在于 devDependency，不会进用户运行时依赖图（`npx openledger` 不带 vitest），
  但对一个**第一天就要公开的开源仓库**，「clone 下来先看到 2 个 critical」是纯负面信号，
  且修它此刻的成本是 0（还没写业务测试），将来是「改一批已写好的测试」。
- 已验证：`vitest@5.1.0` 下 `npm test` 18 个用例全绿、`vitest.config.ts` 无需改动。
- 若将来某任务确实需要降回 2.x（例如某个插件不兼容），降级时**必须**在本文件补记原因。

### 偏差 2（不是偏差，是澄清）：`Question` 未冻结

开发计划 §5.3 的 `RuleHit` 引用了 `Question[]` 但未给定义。为让 `RuleHit` 可编译，
`types.ts` 给出最小形状（`id` / `prompt` / `options` / `answer?`），并**明确标注为未冻结**：
这是六个冻结类型里**唯一**允许后续改字段的类型，语义所有权归 C（T27 会扩展它），
变更只需 C 通知 D，不需五方签字。理由：三问的交互形态还没经过任何真实用户验证，
现在冻结它等于把猜测写进契约。

### 5.1 补记（2026-11-09）：`E3` 赊销确认收入 —— 一次**追加**，不是语义变更

| 项 | 内容 |
|---|---|
| 追加值 | `E3`，语义「**赊销确认收入（已开票、款未到；借 1122 应收账款）**」 |
| 为什么必须补 | 赊销是小微企业最常见的收入形态。缺这一项，「已开票但款未到」只能被**误记为已收款**（E1/E2），错误同时落在两处：1122 应收账款凭空消失、收入确认时点提前一个月。这两处错在试算平衡里**都是平的** |
| 为什么算追加不算变更 | BP2 源 `core/src/types.ts:17` 原文即有 `'E3' // 赊销确认收入`，说明 §5.3 是**转录时漏了一项**，不是设计变更。已有值的语义一个都没动 |
| 对签字约定的影响 | **无**。追加 `EventKey` 值本来就是 §三 允许的「C 单方动作」，不触发五方签字 |
| 落实处 | `types.ts` 的 `EventKey` 联合（紧接 `'E2'` 之后）；`types.test.ts` 穷举表（现为 12 具名 + E99 = 13 键）；原「值域外」反证改用 `E17` |
