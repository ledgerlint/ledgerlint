## 一、输入层：移植而非重写

| 来源 | 处置 |
|---|---|
| BP2 `types / csv / decode / detect / presets / parse` | 移植，去掉 `.js` 扩展名与 `xlsx/pdf` 依赖 |
| BP2 `xlsx.ts` / `pdf.ts` | **不迁**：需要第三方库；v0.1 只吃 CSV |
| 新增 `adapt.ts` | `BankTxn → Transaction`，补 `txnId / sourceHash / account` |

两个刻意的设计：

1. **格式不认识就拒绝并给下一步**，不做"尽量解析"。`.xls` / `.xlsx` / HTML 各有一条明确文案让用户另存为 CSV。读错一个单元格比读不了更糟——用户会拿到一本来路不明的账，还不会怀疑它。
2. **`txnId = sha1(sourceHash + rowNo)`**，不是随机。同一份文件重导必须得到同一批 ID，否则"这笔已经确认过了"无从判断。已实测：重导同一文件 → 新增 0、已存在 3。

## 二、规则 v1：原定 5 类，实际 6 类

原计划 5 类（收客户款 / 付供应商 / 付费用 / 股东投入 / 股东往来）。实施时增加 **E12 预收**，原因：

> 摘要写「预付款/定金」的进账若按 E1 处理，会在**尚未交付时确认收入**。这不是精度问题，是收入确认时点错，且三表全对、任何机检都查不出来。

规则顺序即优先级，`股东` 相关必须排在客户收款之前（已用测试锁住：股东打款备注写「项目款」仍判为股东往来）。

**命中必须有正面证据**（关键词或对方在股东名单），不允许"方向是收入就肯定是客户款"。已用测试锁住三类必须落 `E99`：政府补助、出口退税、押金退回——BP2 的 G31 就是把这三类全出成了收入。

`E99` 草稿**没有分录**。给它编两条"其他应收/应付"会让待处理清单看起来像已处理完。
