## 一、状态展示：**常态不显示，异常必显，按需可查**

### 问题

原首屏有四张卡片常驻：凭证张数 / 链完整性 / 试算平衡 / 告警数。

主理人的判断：**正常情况就不该有问题，这些提示 95% 的场景用不到，只空占版面。**

这个判断成立，而且比"占版面"更严重的一层是：**一个常态为真的指示灯，看过第一周就没人再看它**；而真正出问题那天，它也不会比别的东西更显眼。BP2 的「27 个绿勾没人展开」就是这条规律的实证。

### 规则

| 状态 | 呈现 |
|---|---|
| 链断、试算不平、锚点不符、无法解析的行 | **顶部横幅**，红/黄，写明「是什么 + 该怎么办」，且不得可关闭 |
| 有告警但链完整 | 黄色横幅 + 逐条列出 |
| 一切正常 | **不出现任何状态区块**。页脚一行小字「账本完整 · N 张凭证 · 点此查看校验明细」 |
| 想主动核对 | 点页脚展开明细；或 URL 加 `?diag=1` 自动展开 |

### 边界（不能让步的地方）

1. **异常不能被藏起来**。隐藏的是"正常"，不是"问题"。若因为常态不显示而让一次真实断链变成静默，那比常驻绿勾更坏——这是 BP2「假绿勾」的镜像错误。
2. **导出交付包时校验必须成为闸门**。页面可以不显示，但"生成交付包"这一步若校验不通过，必须阻断（T34/T36 承接）。**状态可以退到幕后，闸门不能。**
3. 页脚那行字必须可点开。用户看不见的东西等于不存在，但"看见它在哪"和"一直显示"是两件事。

### 实现

- 删除首屏四张状态卡片
- `#alert` 容器仅在 `issues` 非空时渲染
- 断链原因翻成人话（`HASH_MISMATCH` → 「某张凭证的内容与它的哈希对不上，可能被手工改过」）；只说"链断了"等于没查
- 页脚一行 + 可展开的明细（张数 / 期间 / 试算 / 链 / 告警）

## 二、准则引用：**归规则库，不进凭证**

### 主理人的判断

把会计准则条目写进凭证是冗余设计，尤其专业财务接手后更用不上。

### 我的修正：判断对，落点要挪一格

引用本身有价值，但价值在**写规则与维护规则**，不在凭证：

| 位置 | 是否保留 | 理由 |
|---|---|---|
| `rules.yaml` 的 `cite` | **保留** | 三个月后有人要改一条映射，得知道它对应哪条规定。这是给维护者看的，不是给用户看的 |
| 凭证的 `BasisRef.CITE` | **删除** | `ruleSnapshot` 已存 `ruleId` + `ruleVersion`，可反查出当时那版规则及其 `cite`。内联等于把同一段文本在几百张凭证里复制几百遍，信息量为零 |

两条补充理由：
- **创始人不需要条文号**，需要的是「一句人话」；**专业财务更不需要**，看科目与摘要就知道依据。条文救不了前者，也不是后者要的东西。
- **手工凭证根本没有规则可引**，`CITE` 在那条路径上永远为空——一个永远为空的字段不是可选，是装饰。

### 变更

- `BasisRef` 从 4 个 kind 收窄为 3 个（`RULE` / `TXN` / `INVOICE`）
- `chain.ts` 的 `BASIS_ORDER` 同步删除 `CITE`
- `types.test.ts` 的穷举断言改为 3 个，并注明「条文归规则库，不进凭证」

`rules.yaml` 尚未实现（T22），实施时 `cite` 为必填字段。

## 三、附：两处「提交信息与代码不符」的更正记录

同一类错误在 12 小时内出现两次，都发生在 commit message 里（比文档更隐蔽，因为没人会去 diff commit 与代码）：

| 提交 | 声称 | 实际 | 处置 |
|---|---|---|---|
| `d69c08b` | 已删除 `RECON` | 未删除 | 已于 `6d8aee4` 真正删除，并加反向测试 |
| `d69c08b` | 已删除 `Question.options` | **未删除，且应保留** | 本条**不删**：三问需要「不确定」这个出口，否则零财务知识用户只能被迫在"是/否"里猜。保留是有意为之，错的是提交信息 |

**机制的结论**：提交信息不是文档，无法被 CI 校验，因此它最容易成为"声明与实现不一致"的藏身处。此后提交信息只写**已跑过验证的事实**，不写意图。
