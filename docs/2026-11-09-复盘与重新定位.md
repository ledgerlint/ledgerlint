| # | 结论 | 依据 | 性质 |

## ③ 根因诊断：表面症状 vs 结构性原因

### 3.1 两版共同的根因（先看这一节）

| 层级 | 内容 |
|---|---|
| **结构性原因 1：验收对象错位** | 产品承诺是「让创始人交得出一本说得清的账」，但可本地验证的只有「断言是否通过」。于是验收标准退化为测试通过率。【事实：审阅报告 §0.2、O1 §0.2 结论三「测试保护实现，而非价值」】 |
| **结构性原因 2：没有真实数据的负反馈环** | 全部验收数据是仿真生成。仿真是「按自己的假设造数据」，永远能过自己的检查。**系统在自我一致的世界里不可能被证伪。**【事实：第三轮 §7；R3 用「外部生成」数据】 |
| **结构性原因 3：断言覆盖边界 = 承诺边界，但两者不重合** | 承诺「账能交出去」，断言只覆盖 L1 形式 + L2 表内恒等。A8 是恒等式（未分配利润吸收未结转损益），A12 只查借方，无跨表勾稽、无外部对齐、无票据真伪。**覆盖不到的地方，恰好是最容易被罚的地方。**【事实：审阅 C1/C4/C5；交接 §6】 |
| **结构性原因 4：用局部可验证信号替代整体目标** | 对账通过率、断言条数、测试数、代码行数——每一个都容易量化，每一个都不是用户价值。指标换了名字，方向仍被牵着走。【事实：意图评估 §4.3】 |
| **结构性原因 5：形态/客群/定价未收敛就开写** | 载体改三次、客群漂三次、商业化三套并存。每次改动都是全量返工，规模增长主要来自返工与补洞，不是来自价值积累。【事实：简报；BP 07/10/11 冲突】 |

### 3.2 为什么规模 +72%、879 全绿，却仍然没有真实用户

| 观察 | 解释 | 性质 |
|---|---|---|
| 41,947 行 vs 24,458 行 | 增量主要来自：①对账/往来/对手方域 9 个阶段（P3.5–P7）；②每轮审计后的补洞（P0–P18）；③27 张表/15 触发器/126 路由的工程纵深。**都是「把已经能跑的部分做得更细」，不是「把没接上的部分接上」。** | 事实（阶段清单见意图评估 §4.1） |
| 819 条测试全绿 | 测试测的是「实现是否符合自身预期」。它能证明没有回归，不能证明「用户会用它做对账」。**测试数与用户价值之间没有单调关系。** | 事实（O1 §0.2 结论三） |
| 三个数（676 / 819 / 879）对不上 | 说明「测试数」这个指标本身没有被单一口径管理。一个连自己测了多少都说不清的项目，用测试数当验收标准是危险的。 | 事实（简报 vs 交接 §13 vs 第三轮 §1.1） |
| 无真实用户 | 因为**从来没有把它交给一个真实用户、用真实数据、走完整闭环**。R3 是仿真、R4 是仿真，UAT 是自测。没有真实摩擦，就没有真实需求输入。 | 事实（第三轮 §7） |

**结论**：规模增长是「在封闭系统里做深」的自然结果，与「外部有用」无关。**这不是执行力问题，是闭环缺了一环。**

### 3.3 为什么两版都会漂移成「会计凭证录入器」

| 环节 | 发生了什么 | 依据 |
|---|---|---|
| 诱因 | 「创始人助手」的核心能力（业务语言输入、时间轴、可信度可视化）**没有本地可验证器**；「凭证/断言」有。 | 意图评估 §5 |
| 机制 | 每次「我这次改对了吗」的答案，最容易被「断言绿了/对账过了」证明；而「创始人能不能自己产出一本账」没有任何数字能证明。 | 意图评估 §4.3 原文 |
| 结果 | 资源持续流向对账/往来/凭证，入口层（A 验收、B 起点、C 翻译）长期空缺。C 处境的对账台左栏取「已录凭证」，**一个从没录过凭证的用户，左栏永远是空的**。 | 意图评估 §3、§5 |
| 定性 | **是定位问题，但以执行问题的形式出现。** 因为定位没有给出「用户可观察、可独立判断通过/失败」的验收物，执行只能退回到「代码自证」。 | 推断·高 |

### 3.4 为什么「断言全绿」和「账是错的」能同时成立

| 断言覆盖到的 | 断言覆盖不到的（= 承诺却在裸奔） | 后果实例 |
|---|---|---|
| 借贷平衡、金额为正、科目存在、期间一致、凭证号连续、红冲成对、期初平、资产负债表**表内**恒等、结转金额=账面净利、期末现金=货币资金、申报额=账面收入、损益归零、责任链可回放 | 科目**语义**对不对、**跨表**勾稽（未分配利润滚动）、收入**确认时点**、票据**真伪**、现金流**分类**、辅助核算**对象** | 「管理费用错记销售费用」三表全对、27 断言全绿（交接 §7.3）；「工资三费贷方不记人」按人看 −375，总账净额 0 全过（第三轮 §3.3）；「收入直记 3104」全绿（第三轮 §3.4）；「期初资产漏提折旧 5.7 万」试算平衡照旧通过（R3 §2.1） |

**验收标准的缺陷定义**（这是本次诊断最重要的一条）：

> 一个验收标准如果是「系统与自己一致」，它只能证明「没有内部矛盾」，不能证明「对外部事实为真」。
> 财务软件的外部事实是：**银行流水、发票、代账给的报表、税局申报数**。任何一条断言若不与这四者之一对齐，它就只是装饰。
> A8 之所以危险，不是因为错，而是因为**它永远为真**——一个永远为真的检查比没有检查更糟，因为它制造虚假安全感（审阅 O4 原文）。

**正确验收标准的三个必备成分**（替代「879 全绿」）：
1. **外部对齐**：与流水/发票/代账报表逐项比对，差异必须逐条解释，不允许「默认吸收」。
2. **反向构造**：每条 BLOCK 级断言必须有一个「本该报但可能不报」的反例探针，探针库是资产。
3. **局限随结论输出**：结论（绿勾/交付包）必须随身携带「我没查什么」。

### 3.5 两版各自特有的死因（补充）

| 版本 | 特有死因 | 依据 |
|---|---|---|
| BP1 | 把「正确性」押在 LLM 上。LLM 无法保证不编造，规则引擎只是补丁；一旦 LLM 输出不可信，整条链路不可信。 | 简报（编造 500 元/微信账户、四轮死循环） |
| BP2 | 把「正确性」押在断言上。断言覆盖不到语义，于是「精密且错误」。且工程纵深（store.ts 8072 行、126 路由、24 e2e）吃掉了本应用于入口层的预算。 | 交接 §7.10；审阅 §2.4 |

| 服务层 | BP2 `server` 126 路由 2.7k 行 | 随接口收窄重写 |
| 关键词场景机 | BP1 `scenarios.ts` 813 行（含冰柜/次卡/美团） | 第一版客群残留；模式本身（关键词判方向）是错的 |
| 与首切口无关的模块 | 工资/研发加计/固资卡片/OFD/发票查验/脱敏专利/看板/尽调/runway/UAT 面板 | 无一能用一句话说明它服务「首个 100 用户」 |
| MCP | BP2 `mcp` 984 行 | 留待 V1 作为「可编程接口」，不是 MVP |

**复用建议一句话**：**只带走 BP2 的 `core/` 纯函数 + `import/` 流水解析 + 少量组件与 `LIMITATIONS` 表，其余全部归档。** 不要试图「瘦身」store 与 web——它们与旧形态深度绑定，改造比重写贵。

## ⑤ 目标客户重新定义

### 5.1 三个可触达细分（按优先级排序）

#### S1（首选）刚经历一次「账不放心」时刻的技术型小微创始人 / 技术合伙人

| 维度 | 描述 |
|---|---|
| 谁 | 有限责任公司，1–10 人，小规模纳税人，年营收 100–1000 万，创始人或技术合伙人兼管财务，没有专职会计 |
| 在什么时刻 | 季度报税前一周 / 要申请贷款或融资尽调 / 收到税务风险提示或被约谈之后 / 刚换掉不满意代账的第一个月 |
| 因为什么痛 | 代账给了两张表，**看不懂，也无法判断对不对**；想自己核对，但手上只有银行流水和发票，不知道怎么变成会计账 |
| 现在怎么凑合 | Excel 记流水 + 微信问代账 + 「年底再说」；或干脆不看 |
| 为什么可验证 | 他手上有流水 + 发票，**正好是我们能处理的全部输入**；他的任务就是「核对/自证」，不需要完整账套 |
| 规模信号 | 小规模纳税人 + 小微企业是政策口径上的最大群体【推断·中，需市场数据补】 |

#### S2（次选）接外包的独立开发者 / 自由职业技术人（个体户或一人工作室）

| 维度 | 描述 |
|---|---|
| 谁 | 个人或一人工作室，收入来自多个平台/客户，需要自证收入成本 |
| 在什么时刻 | 平台结算对账 / 开票 / 年度汇算 / 被平台或客户要求提供财务证明 |
| 因为什么痛 | 收入散在多平台、成本票据散乱；Excel 对不上；请代账又觉得不值 |
| 现在怎么凑合 | Excel + 手动开票 + 平台后台截图 |
| 为什么可验证 | 输入仍是流水 + 发票；任务更窄（收入成本归集），更容易做对 |
| 为什么排第二 | 单客价值低、付费意愿弱，但**开源口碑传播力强**（技术人聚集地） |

#### S3（第三，长期）小型代账/财税工作室的初级会计或兼职会计

| 维度 | 描述 |
|---|---|
| 谁 | 服务 10–50 家小微客户的代账工作室里的执行会计 |
| 在什么时刻 | 每月批量把客户流水转成凭证草稿 |
| 因为什么痛 | 手工从流水录凭证慢、易错、重复 |
| 现在怎么凑合 | 金蝶/用友/易代账等代账软件 |
| 为什么排第三 | **他们有完整账套**，与「只有流水」的验证前提不符；且已用成熟软件，替换成本高 |
| 为什么仍要留 | ①是「未来兼容专业财务」的自然入口；②是 B2B 付费的可能来源；③他们的复核意见是最好的规则校准器 |
| 明确策略 | **不替代代账软件，做它的「上游草稿生成器」**（BP `10-商业化路径批判分析 §4.4` 的「二道防线」判断仍成立） |

### 5.2 首个 100 个用户从哪来（具体到渠道与动作）

> 目标不是「曝光」，是「100 个真实安装 + 30 个提交 issue」。渠道按「技术人密度 × 财务相关性」排序。

| # | 渠道 | 具体动作 | 预期产出（2026-12-31 前） |
|---|---|---|---|
| 1 | GitHub | 发布 v0.1 + 仓库内自带可跑 demo 账套（**fixtures 入仓，不依赖外部路径**——修 BP1 X1 缺陷）+ 一段 30 秒 gif | 300–800 star；star→安装转化是主漏斗 |
| 2 | Show HN / Reddit r/plaintextaccounting / r/selfhosted / r/Bookkeeping | 一篇《用一条命令把银行流水变成会计能复核的凭证包》+ 真实脱敏案例 | 50–150 安装；海外技术人第一批反馈 |
| 3 | V2EX「分享创造」/ 即刻 / 掘金 / 思否 | 中文长文 + 可复现 demo；标题强调「不替代代账，做交付前自检」 | 国内技术创始人第一批 |
| 4 | 独立开发者社区（w2solo / 电鸭 / Indie Hackers 中文） | 「我把自己踩过的账坑做成了工具」叙事 + 招募 10 名种子用户做 1 对 1 | 10 名深度种子用户（最关键） |
| 5 | 知乎「代理记账 / 小企业会计」话题 + B 站会计 UP 主 | 不做硬广，做「代账给的账怎么自查」的科普，文末放工具 | 触达 S3 与 S1 的交叉人群 |
| 6 | 本地（成都）创业社区 / OPC 社群 | 以「工具伙伴/讲师」身份进 1–2 场，不发传单，做「30 分钟把你的流水变成凭证包」现场演示 | 3–5 家真实数据提供者 |
| **7** | **母校创业中心 → 初创学生公司**（2026-11-09 新增，**真实数据主渠道**） | 由主理人协调，以「给入驻学生公司做一次免费账务体检」为切口进场；要流水+发票+代账报表，给机检报告 | **W2 前 2 家、W7 前 3–5 家真实账套** |

> **为什么第 7 条排在最前**：前 6 条解决的是「曝光」，第 7 条解决的是「**真实数据**」——而真实数据是前两版唯一没拿到、也唯一无法自我伪造的东西。它同时是 S1 客户的天然样本（学生公司=小规模纳税人+无专职会计+常被代账敷衍）。**这条渠道不通，整个切口就不成立**（见文档二 §5.1 生死点）。

**冷启动纪律**：前 100 个用户必须能「自己装上、自己跑通 demo、自己提一个 issue」。做不到说明上手路径有问题，先修路径再拉人。

### 5.3 在「只有流水/发票」的现实下，哪一段任务能被真实验证

| 任务段 | 能否用现有数据验证 | 说明 |
|---|---|---|
| 银行流水解析/去重/幂等 | ✅ 完全可验证 | 有原始文件即可 |
| 流水 → 凭证草稿（科目 + 方向 + 税分离） | ✅ 可验证 | 与会计/代账的人工结果逐条比对，算「分录一致率」 |
| 流水 ↔ 发票勾稽 | ✅ 可验证 | 两边都有；未匹配必须显形 |
| 凭证草稿 → 交付包（凭证清单 + 科目余额表 + 利润表草稿 + 机检报告 + 局限） | ✅ 可验证 | 与代账给的同期报表比对，差异逐条解释 |
| 期末结账 / 年结 / 汇算清缴 | ⚠️ 部分 | 需要完整期末数据才能验证；MVP **不做完整结账**，只做「月度草稿包」 |
| 报税数字正确性 | ❌ 不可验证 | 需税局申报数对齐；MVP 不做申报，只做数据准备并标注局限 |
| 票据真伪 | ❌ 不可验证 | 需查验接口；MVP 明确不做、写进局限 |

**结论**：切口必须缩到 **「流水 + 发票 → 凭证草稿 → 可交付包」**。这一段每一环都能被真实验证，且正好是 S1 最痛的一段。**「可交付包」不是完整账套，是「交给代账/会计复核的输入」。**

### 5.4 明确不服务谁

| 不服务 | 原因 |
|---|---|
| 一般纳税人（需进项抵扣/专票管理） | 复杂度高、验证数据更难拿；MVP 不做 |
| 需要直连税局自动申报的 | 合规与对接成本高；MVP 只做数据准备 |
| 多主体/集团/合并报表 | 与「单账套单用户」边界冲突 |
| 餐饮零售进销存（库存数量/加权平均） | 第一版客群残留；与「流水+发票」切口无关 |
| 需要「无人值守全自动做账」的 | 与「每条草稿必须人确认」的诚实设计冲突 |
| 已用成熟代账软件且满意的代账机构 | 不替代，只做上游工具 |
| 完全不懂电脑、不愿用命令行/浏览器的人 | 不是目标客群；不为他们做桌面安装包（见 ⑥） |

## ⑥ 产品形态定义（一次钉死）

### 6.1 载体：`npx` 一行启动的本地 Web（唯一答案）

| 选项 | 判断 | 理由 |
|---|---|---|
| CLI 纯命令行 | ❌ | 非会计用户需要看凭证表、点确认；纯 CLI 无法承载 |
| 桌面壳（Tauri/Electron） | ❌ | 签名/公证/跨平台打包是 solo 开发者的无底洞；开源分发靠安装包转化率极低；BP1 已证载体反复改的代价 |
| 单二进制 | ❌ | 与「开源可 hack、可贡献」冲突；构建链复杂 |
| **`npx` + 本地 Web** | ✅ **唯一** | 一行跑起来（开源分发的最高转化）；零安装包；跨平台；贡献者 `git clone && npm i` 即可开发；浏览器天然有表格与确认交互；沿用 BP2 已验证的 127.0.0.1 + token 模式 |

**具体形态**：`npx openledger ./mybook` → 自动开浏览器到 `127.0.0.1:<port>` → 三页（导入 / 确认 / 交付包）。数据在当前目录，不上云。

### 6.2 数据边界：append-only 纯文本 journal 为唯一真相

```
mybook/
  book.json                 # 主体、准则、纳税人身份、征收率、参数版本
  opening.json              # 期初（仅资产负债科目，白名单强制）
  journal/2026-01.jsonl     # 每月一行一个已确认凭证，含 hash + prevHash（哈希链）
  drafts/2026-01.jsonl      # 草稿（可改），确认后追加到 journal
  sources/2026-01-bank.csv  # 原始流水（内容 hash 校验）
  sources/2026-01-inv.csv   # 原始发票
  rules.yaml                # 规则包（版本锁定）
  exports/                  # 交付包
```

| 决策 | 内容 | 理由 |
|---|---|---|
| 真相源 | **append-only JSONL**，不是 SQLite | 可 `git diff`、可备份（拷文件）、可被其他工具消费（PTA 生态）、审计链就是文件本身 |
| 不可变 | 追加即事实；红冲 = 追加反向凭证；哈希链断点可检 | 用「只追加 + 哈希链」替代 BP2 的「触发器 + 应用层」三层，更简单更诚实 |
| 查询 | 启动时全量载入内存索引 | 小企业 <1 万凭证/年，内存足够；**SQLite 仅作可选派生缓存，永远不是真相源** |
| 兼容 | 提供 Beancount 风格导出（P1） | 接入 PTA 生态，放大开源影响力 |

【推断·高】这个存储选择是「开源可审计」承诺的技术兑现：**用户能 `git log` 看到每一笔账是谁、何时、按哪条规则加的。**

### 6.3 AI 到底要不要：MVP **不接 LLM 进账务路径**

| 判断 | 内容 | 依据 |
|---|---|---|
| MVP 不接 | 任何科目编码、金额、方向**只能来自规则引擎或人工输入**；LLM 在类型层面无写权限 | BP1 事实：LLM 编造 500 元与微信账户、四轮死循环 |
| 为什么禁 LLM 不是根因 | BP2 禁了 LLM 却成了录入器，说明「用户看不懂」不是 LLM 缺失，是**缺「业务语言 → 会计动作」的规则化翻译层** | 意图评估 §3 C 出口错位 |
| 替代方案 | ①**三问推导事件**：钱动了吗 / 交付了吗 / 开票了吗 → 系统推导 E1/E4/E12；②每条草稿给「一句人话 + 为什么是这个科目 + 依据哪条规则/哪张发票」；③不确定就显形，不替用户拍 | 审阅 §3.2 H1「事件从输入变成输出」 |
| 若将来要 AI | 唯一允许位置：**已确认事实之上的只读解释/检索/摘要**（「把这个月的异常用大白话讲一遍」）。BYOK、默认关闭、可完全离线；LLM 输出不得写回账务数据 | 沿用 BP1 `harness/tools.ts` 只读白名单 + `llm-port.ts` 的正确接口 |

**铁律（写入代码约束）**：`entry.accountCode` / `entry.amountCents` / `entry.direction` 的赋值点必须可枚举；任何 LLM 通道不在这三个赋值点的调用图上。

### 6.4 核心交互范式（第一次打开 → 第一笔账落地，≤5 步）

1. `npx openledger ./mybook` → 浏览器打开；填主体信息（3 个字段：名称、纳税人身份、征收率）。
2. 拖入**银行流水**（CSV/Excel，自动列映射）+ **发票台账**（可选）。
3. 系统逐条生成**凭证草稿**，每条带 `OK / WARN / BLOCK` + 一句人话（例：「8,800 付给税务局 → 应交税费—增值税」）。
4. 用户逐条确认或改科目（只有少数需要改；BLOCK 必须处理，WARN 可批量过）。
5. 点「生成本月交付包」→ 凭证清单 + 科目余额表 + 利润表草稿 + 机检报告 + **局限说明**。

**终点是「可交付包」，不是「结账」**。这是与两版最大的形态差异：**产品在「交付前」结束，不在「申报后」结束。**

### 6.5 与「未来兼容专业财务 / ERP」的关系：**架构预留，不是产品承诺**

| 项 | 定性 | 具体机制 |
|---|---|---|
| 多账套 / 多用户 / 权限 | **架构预留，不承诺** | 数据层预留 `bookId`；**但在满足硬门禁前不实现** |
| 防范围膨胀硬门禁 | 三条件**同时**满足才允许开工：①≥100 名真实周活用户；②≥10 个独立 issue 明确要求多主体/多人；③journal 格式连续 2 个 minor 版本未变 | 任一不满足 → 不开工；写进 CONTRIBUTING 与 ROADMAP |
| 每个需求的门 | 必须一句话回答「它如何服务首个 100 用户」，答不上不进 P0 | 写进 PR 模板 |
| 代码预算 | core+server+web 合计行数设上限（建议 15k），超了先删后加 | CI 统计 |

**对主理人的提醒**：BP2 的 P0–P18 已经演示了「补洞式膨胀」的代价。门禁不是官僚，是**防止第四次同一种坑**（16→21→24→27）的唯一机械手段。

## ⑦ 价值主张与竞品矩阵

### 7.1 一句话价值主张（让不懂会计的人听懂）

> **把银行流水和发票丢进去，出来一份会计一看就懂、能直接复核的凭证包——在交给代账或税局之前，自己先对一遍。**

关键词是「**交付前自检**」，不是「代账」，也不是「记账 App」。

### 7.2 竞品对比矩阵

> ✅ 赢 / ＝ 平 / ❌ 主动认输

| 维度 | Excel 模板 | 代账 | 随手记/挖财 | Beancount/PTA | 金蝶/用友小微 | **OpenLedger（本产品）** |
|---|---|---|---|---|---|---|
| 复式记账正确性 | ❌ 靠人 | ✅ | ❌ 单式 | ✅ 但靠人写 | ✅ | ✅ 规则引擎生成 |
| 零财务知识可用 | ❌ | ✅ 但黑箱 | ✅ 但非会计 | ❌ 要学语法 | ＝ 偏专业 | ✅ 三问推导 |
| 流水/发票→凭证自动化 | ❌ | ✅ 人工 | ＝ 只记流水 | ❌ 手写 | ＝ 半自动 | ✅ **核心能力** |
| 交付物可被会计复核 | ＝ 手工 | ✅ | ❌ | ＝ 需转换 | ✅ | ✅ **交付包 + 局限** |
| 数据本地 / 可审计 / 可带走 | ✅ | ❌ 在代账手里 | ❌ 云 | ✅ | ❌ 云 | ✅ **纯文本 + 哈希链** |
| 开源可扩展 | ❌ | ❌ | ❌ | ✅ | ❌ | ✅ **AGPL + 规则包** |
| 一次录入成本 | ❌ 高 | ✅ 外包 | ✅ 低 | ❌ 高 | ＝ | ✅ 流水批量 |
| 价格 | 免费 | 1200–3600/年 | 免费/低 | 免费 | 数千/年 | **免费开源** |
| 移动端 | ❌ | ＝ | ✅ | ❌ | ✅ | ❌ **主动认输** |
| 报税直连 | ❌ | ✅ | ❌ | ❌ | ✅ | ❌ **主动认输** |

**赢的格子**：①开源可审计 + 数据本地 + 交付包可复核（唯一同时满足）；②流水/发票→凭证自动化且**可解释**；③零财务知识可用（三问）且**不黑箱**。
**主动认输的格子**：移动端（输随手记）、报税直连与批量效率（输代账 SaaS 与金蝶）、纯文本极客灵活性（输 Beancount）。

### 7.3 开源本身是不是卖点

| 判断 | 内容 | 依据 |
|---|---|---|
| 是，且在财务语境下更硬 | 「可审计、无后门、数据不出本机」在财务软件里是**信任的核心**。用户把最敏感的数据交给你，闭源 = 要求无条件信任；开源 = 可验证。哈希链 + 纯文本 + 可复现构建，三者叠加才构成「你可以自己验证碰你钱的代码」 | BP `10 §4.3`「信任不对称」是真护城河 |
| 边界 1：免费 ≠ 可靠 | 会有人怀疑「免费的东西不可靠」。对策：可复现构建 + 发布哈希 + 至少一次外部会计/安全审阅 + 明确责任边界（辅助工具免责）+ 有节奏的 release | BP `10 §4.2` 责任主体判断 |
| 边界 2：开源换不来「不懂技术」的用户 | 开源换的是技术型 OPC / 开发者口碑，**不是 C 端个体户**。所以 S1/S2 是技术型，S3 才是非技术 | BP `10 §3.2`「开源能换 C 端个体户用户基本不能」 |
| 边界 3：开源也会被抄 | 壳开源换信任与贡献；**规则包/评测集作为商业边界**（open-core） | BP `07 §4` 判断仍成立 |

## ⑨ 风险与失效条件

| # | 风险 | 触发信号 | 应对 / 失效条件 |
|---|---|---|---|
| R1 | **真实数据仍拿不到**（原确认只有流水+发票；2026-11-09 已开创业中心渠道） | **W2 结束仍无第 1 份真实流水** | 先换备选渠道再给 2 周；W4 仍无 → 转向纯 PTA 工具或暂停（见文档二 §5.1） |
| R2 | **会计正确性无法自证** | 真实回归分录一致率 <80% 且规则难提升 | 说明切口或规则库错；先扩规则再评估，不靠加断言 |
| R3 | **范围膨胀复发**（最可能） | 出现「新增模块」而「入口层仍未完成」；代码行数无解释增长 | 机械门禁 6.5 + 每需求一句话门 |
| R4 | **开源被白嫖 / 零贡献** | 6 个月 star<100 且无外部 PR | 影响力优先，接受；商业边界靠规则包；仍无信号则判定影响力路径不成立 |
| R5 | **AGPL 吓退企业用户** | 企业用户明确因许可证放弃 | 目标客群是技术创始人，可接受；双许可列为 W36+ 选项 |
| R6 | **单人 40h/周 burnout** | 连续 2 周无「可交付物」 | 7 周路线必须可裁剪，每周必须有可交付物（文档二 §5） |
| R7 | **「交付包」被误解为「报税依据」** | 用户拿交付包直接申报 | 交付包首行固定免责 + 局限说明强制输出；文案层拦截 |
| R8 | **纯文本存储性能不足** | 单账套 >2 万凭证时载入 >5 秒 | 加 SQLite 派生缓存（不是真相源）；或按年分片 |

**总失效条件（触发则整体转向）**：2026-12-31 后仍无「1 家真实企业 + 月度流水/发票 + 分录一致率 ≥90% + 差异可解释」的案例，则证明「交付前自检」这个切口不被需要，应停止扩张、只保留 core 作为 PTA 工具开源。
